Signing Keys Tool

A small Java command-line tool that creates and checks RSA key pairs for digital signatures, one pair per environment or per client. It needs nothing but a JDK: no OpenSSL, no libraries.

1Why this tool exists

Whenever one app signs something and other apps check the signature, you need a key pair. Common cases are JSON Web Tokens signed with RS256, webhook payloads, license files, and signed configuration or documents. This tool makes RSA pairs for signatures made with SHA256withRSA, which is what JWTs call RS256 (RFC 7518). A pair has two halves:

  • a private key, which signs. Only the one app that signs may have it.
  • a public key, which verifies signatures. Every app that checks them gets a copy. It can't be used to sign anything.

Making a pair by hand is easy to get subtly wrong: the wrong file format, a key the loading code rejects, a public key on one server that doesn't match the private key on another, or a pair nobody remembers to replace. This tool handles all of those. It writes the files in the standard formats Java and most crypto and JWT libraries load. It reads them back before it says it succeeded. It prints a short fingerprint so two servers can confirm they hold the same public key. It also records an expiry date, so you get a warning before the pair needs replacing.

An analogy: a signet ring and a wax seal

Private key = the signet ringOnly the signer has it. Pressing it into wax (signing) is what makes a document genuine.
Public key = a photo of the sealEvery gatekeeper keeps one. They can tell a real seal from a fake, but they can't make a seal from a photo.
Fingerprint = the photo's serial numberA short code two people can read out over the phone to make sure they have the same photo.
Certificate = a "replace by" dateStamped on the back of the photo, so the gatekeeper is reminded when to ask for a new ring.

Why not just use keytool or OpenSSL?

Both can make an RSA pair, but neither gets you all the way to files you can hand out safely. keytool comes with every JDK, but it keeps keys inside a keystore and has no command that exports the private key as a PEM file (keytool docs). OpenSSL can write the files, but it's a separate install on Windows, and the commands for a PKCS#8 private key, a matching public key and a certificate are easy to get wrong (OpenSSL docs). This tool uses keytool for the one step plain Java can't do, which is signing the certificate. It writes the PEM files itself and adds the checks around them.

2Quick start

You need a JDK, version 8 or later, that includes keytool (a standard JDK has it next to java). You also need Apache Maven to build. The tool runs on Windows and Linux, and the same jar works on both.

# build: compiles, runs the tests, and writes signing-keys-tool.jar into the project folder
mvn package

Then run it in any one of three ways. They behave the same, and the launchers pass the exit code through.

WhereCommand
Any system, plain Javajava -jar signing-keys-tool.jar <command> ...
Windows launchersigning-keys-tool.cmd <command> ...
Linux / macOS launcher./signing-keys-tool.sh <command> ...

The launchers find the jar next to the script, even through a symbolic link, so you can run them from any folder. If the .sh file isn't executable, run chmod +x signing-keys-tool.sh once.

# a pair for production, written under ./keys/prod
java -jar signing-keys-tool.jar generate --env prod --out keys

# a separate pair for one client, under ./keys/prod/acme
java -jar signing-keys-tool.jar generate --env prod --client acme --out keys

# a QA pair that is valid for one year
java -jar signing-keys-tool.jar generate --env qa --days 365 --out keys

# read a pair back and check it (use keys\prod\acme on Windows)
java -jar signing-keys-tool.jar check keys/prod/acme
Always pass --out for real keys

Without --out, files go to signing-keys inside the Java temp folder (java.io.tmpdir), for example C:\Users\<you>\AppData\Local\Temp or /tmp. That suits a test run. A temp folder is no place to keep a private key.

3How it works

The tool is six small classes with no dependencies outside the JDK. One class reads the command line, one handles a key pair on disk, and two helpers do the low-level work.

Command line

SigningKeysTool

Reads the arguments, checks every option, prints the result, and turns errors into exit codes.

↓
One pair on disk

KeyFiles

Writes the three files. Reads them back the way an app that signs or verifies would. Works out the fingerprint and expiry, and limits the private key file to its owner.

↓
Makes the pair

Keytool

Runs the JDK's own keytool to create the RSA pair and a self-signed certificate. Then loads the result with java.security.KeyStore.

File format

Pem

Wraps binary key bytes (DER) in PEM text: base64 in 64-character lines between BEGIN and END lines. Also unwraps PEM back to bytes.

Exit code 2

UsageException

The command line is wrong. The tool prints the message and the usage text.

Exit code 1

FailException

The command line is fine but the work failed. The tool prints the message.

Why it runs keytool

The expiry date lives in an X.509 certificate, and a certificate has to be signed. The JDK has no public API for building one. The usual workaround is a library such as Bouncy Castle, but this tool takes no dependencies. Instead it runs the keytool that sits in the bin folder of the Java running the tool (keytool docs). That keeps everything on one Java installation. The tool never parses keytool's text output: it reads the keystore keytool wrote through the standard KeyStore API (KeyStore docs).

What generate does, step by step

  1. ValidateCheck every input--env, --client and --name must match [A-Za-z0-9][A-Za-z0-9._-]{0,63}, because they become folder and file names. --bits must be 2048, 3072 or 4096. --days must be 1 to 3650.
  2. ValidateRefuse to overwriteIf any of the three files already exists, stop with exit code 1 and change nothing, unless --force was given.
  3. MakeRun keytool in a throwaway folderkeytool -genkeypair with RSA, SHA256withRSA, the chosen validity and the common name CN=<name> <env> [<client>]. It writes into a PKCS#12 keystore in a new temp folder. The keystore password is a random 160-bit value passed through the SIGNING_KEYS_PASSWORD environment variable (-storepass:env), so it never appears on a command line.
  4. MakeLoad the result, then delete the keystoreRead the private key and certificate through KeyStore, then delete the temp folder. If it can't be deleted, the tool warns loudly, because the keystore holds the private key. Nothing has been written to your folder yet, so a keytool failure leaves it as it was.
  5. WriteWrite the private key, locked down firstCreate the file empty, limit it to its owner (POSIX rw-------, or on Windows an access list with one entry for the owner), and only then write the key bytes. That way the key is never readable by others, even for a moment.
  6. WriteWrite the public key and the certificateThe public key goes in as X.509 SubjectPublicKeyInfo, the certificate as an X.509 certificate. Both are PEM with LF line endings.
  7. VerifyRead everything back with checkThe same check you can run later (below). So generate never reports a pair it couldn't load.
  8. VerifyPrint the reportThe full path of each file, key size, fingerprint, expiry date and pair OK.

What check does

check reads the files the way an app written in Java would, with KeyFactory and the standard PKCS#8 and X.509 key specs. A pair that passes here will load there. Only the public key is required: an app that only verifies signatures has no private key, and pairs made by other tools have no certificate.

4The three files

A pair is written to <out>/<env>[/<client>]/. The file names start with --name, which defaults to signing.

FileFormatWho should hold it
<name>-private.pemPKCS#8 (RFC 5208), first line -----BEGIN PRIVATE KEY-----, no passwordThe one app that signs
<name>-public.pemX.509 SubjectPublicKeyInfo (RFC 5280), first line -----BEGIN PUBLIC KEY-----Every app that verifies signatures
<name>-cert.pemSelf-signed X.509 certificate for the public key, first line -----BEGIN CERTIFICATE-----. Its notAfter date is the pair's expiry.Anyone who runs check on a copy of the public key

All three are PEM files: base64 text between BEGIN and END lines, wrapped at 64 characters (RFC 7468).

signing-keys-tool

Writes all three files into one folder for the environment (and client).

→

The fingerprint

The fingerprint is the SHA-256 hash of the public key's DER bytes (the SubjectPublicKeyInfo inside the PEM), written as 64 lowercase hex characters. Two copies of a public key match exactly when their fingerprints match. You can get the same value with OpenSSL (OpenSSL docs):

openssl rsa -pubin -in signing-public.pem -outform DER | openssl dgst -sha256
What the expiry does, and doesn't do

The two key files carry no expiry. The date is only in the certificate, and apps usually load only the two key files. So nothing enforces the expiry when a signature is verified: an "expired" key keeps working there. The expiry exists so check can tell you to replace the pair in time. A pair made without a certificate, by another tool for example, can't be given one later. Generate a new pair to get an expiry.

Never commit a private key

The repository's .gitignore already excludes keys/ and *.pem.

help, --help and -h print the usage text and exit 0.

Command-line rules

  • check refuses --bits, --days and --force, which only apply to generate.
  • generate refuses a bare folder argument. Use --out, --env and --client.
  • check takes a folder or --env/--client/--out, not both, and at most one folder.
  • An option followed by another --option counts as having no value. Unknown options are refused.
  • --env, --client and --name may contain letters, digits, ., _ and -. They must start with a letter or digit and be at most 64 characters. That rules out .. and slashes, so a name can't escape the output folder.

Exit codes

CodeMeaning
0Done. This includes check with an expiry warning.
1The work failed: a file exists, a key doesn't load, the pair doesn't match, the key has expired, or keytool failed.

6Scenario walkthroughs

The output below is what the tool prints. Paths are shortened, and your fingerprint will differ because every pair is new.

ASetting up keys for a new client

Production needs its own pair for the client acme:

> java -jar signing-keys-tool.jar generate --env prod --client acme --out keys
Created the signing key pair for prod / acme
  private key  C:\work\keys\prod\acme\signing-private.pem
  public key   C:\work\keys\prod\acme\signing-public.pem
  certificate  C:\work\keys\prod\acme\signing-cert.pem
  key          RSA 2048 bits (SHA256withRSA / RS256)
  fingerprint  SHA-256 of the public key: 1aac9141ce06d3a01d8e64354337a8833c7e16c36af16b7d996c8f8cbba751b5
  expires      2031-10-11 (1825 days left)
  check        pair OK

The private key goes only to the app that signs. Every app that verifies signatures gets the
public key only. Keep the private key out of source control. Keep the certificate beside the
public key, so 'check' can warn there before the key expires.

Next: copy signing-private.pem to the app that signs, and nowhere else. Copy the public key and the certificate to every app that verifies. Write down the fingerprint.

BConfirming a server has the right public key

A server that only verifies signatures holds the public key and the certificate. Run check there:

> java -jar signing-keys-tool.jar check C:\apps\verifier\keys
Checked C:\apps\verifier\keys
  public key   RSA 2048 bits (SHA256withRSA / RS256)
  fingerprint  SHA-256 of the public key: 1aac9141ce06d3a01d8e64354337a8833c7e16c36af16b7d996c8f8cbba751b5
  expires      2031-10-11 (1825 days left)
  check        public key only. There is no signing-private.pem here, so no pair was checked.

If the fingerprint matches the one printed by generate, the server has the right key. If it doesn't, every signature from the signing app will fail there. Recopy the public key.

CA key nearing its expiry date

With 30 days or fewer left, check still exits 0 but adds a line on the error output:

warning: the key expires on 2031-10-11, in 21 days. Plan a new pair.

After the date has passed, check fails with exit code 1:

error: The key expired on 2031-10-11 (…\signing-cert.pem). Generate a new pair.

If you run check from a scheduled job, a warning doesn't change the exit code. Watch the error output too, or you'll only notice once the key has expired.

DRunning generate twice by accident

error: C:\work\keys\prod\acme\signing-private.pem already exists. Use --force to replace it. Anything signed with the old pair stops verifying once the new public key is in place.

Exit code 1, and nothing on disk changes. --force is the only way past this, and the message says why that matters. Anything signed with the old private key won't verify against the new public key. For JWTs, that means every token issued so far stops working.

EAn old key in PKCS#1 form

A private key that starts with -----BEGIN RSA PRIVATE KEY----- is in the older PKCS#1 form (RFC 8017). Java's PKCS#8 key loader can't read it, so check fails and shows how to convert it:

error: Cannot read …\signing-private.pem as a PKCS#8 private key (it must start with -----BEGIN PRIVATE KEY----- and have no password). It looks like a PKCS#1 key. Convert it: openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in <old file> -out <new file>

FA typo or an unsafe name

> java -jar signing-keys-tool.jar generate --env ../x
error: --env '../x' is not allowed. Use letters, digits, '.', '_' and '-' only, start with a letter or digit, and keep it to 64 characters.

7Safety measures built in

Most of the code is about keeping a private key from ending up somewhere it shouldn't, or a broken pair from reaching production.

Overwriting a live pair by mistakeRefuses if any of the three files exists, unless you pass --force. The message warns that anything signed with the old pair stops verifying.
A name escaping the output folder--env, --client and --name must match a safe pattern, so .., slashes and drive letters are refused.

8Choosing options

One pair per environment, or per client?

Per environment
Use --env alone when one app signs for everyone in that environment and every verifying app may accept anything it signs.

Per client
Add --client when something signed for one client must not be accepted for another. Each client also gets its own replacement schedule, so replacing one client's pair doesn't affect the others.

Never
Don't share a pair across environments. A QA signature would verify in production. The folder layout (<out>/<env>/…) is built to keep them apart.

One pair per job

Separate jobs
Give each kind of signature its own pair with --name, for example --name jwt and --name webhooks in the same environment folder. Replacing one then doesn't break the other.

Not for encryption
Use these pairs for signatures only. Key-management guidance says each key should have one purpose (NIST SP 800-57), and check only tests signing.

Key size: --bits

2048 (default)
The smallest size RS256 allows (RFC 7518 §3.3), and the fastest to sign and check.

3072 or 4096
When a security policy asks for it. An RSA signature is as long as the key, so every signature grows from 256 bytes to 384 or 512 bytes, and signing gets slower.

Lifetime: --days

Production
The default 1825 days (5 years) suits keys that are expensive to replace, since replacing one invalidates everything signed with it.

Dev / QA
Shorter, such as --days 365, so replacing a pair stays routine.

Keep in mind the expiry only drives check's warning. It isn't enforced when signatures are verified.

Tests

SigningKeysToolTest runs the tool end to end. Each test calls SigningKeysTool.run(...) with captured output streams in a temporary folder. The expiry tests swap in a Clock moved forward in time, so they can test "29 days left", "31 days left" and "expired" without waiting. The 39 tests cover file layout, name validation, overwrite protection, file permissions, fingerprints, PKCS#1 detection, the expiry rules and cleanup of the temp keystore.

10Limits and open questions

  • The expiry is advisory. Apps usually load only the two key files, so an expired pair keeps working there. Only check looks at the date.
  • No rollover. Replacing a pair invalidates everything signed with the old one. The tool has no key IDs (such as the JWT kid header) and doesn't publish a key set, so it can't run old and new pairs side by side during a changeover. How to replace a production pair without disruption is left to the apps that use it.
  • Signatures only. check tests signing and verifying. The tool doesn't test or advise on using a pair for encryption.
  • The private key has no password. PKCS#8 without encryption is what Java's KeyFactory loads directly. Protection relies on file permissions and where you keep the file.
  • Windows permissions are strict. On Windows the private key file ends up with a single access entry, for its owner. No other account is listed, which may matter for services running under a different account.
  • Other pairs can't get an expiry. A certificate can't be added to a pair made by another tool. Generate a new one.
  • keytool is required. A trimmed-down Java runtime may not include it. generate then fails with "keytool not found … Run this with a JDK." check doesn't need it.
  • The fingerprint isn't a JWK thumbprint. It hashes the DER public key, not the JSON form defined in RFC 7638, so it won't match a kid derived that way.
  • macOS isn't tested. The .sh launcher's usage mentions macOS, but the README lists Windows and Linux, and CI runs only those two.
  • Your own app is out of scope. check proves the files load with Java's standard key classes. Confirm once, in a test environment, that your own app loads them too.
